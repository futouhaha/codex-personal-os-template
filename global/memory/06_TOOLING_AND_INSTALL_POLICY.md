# 工具和安装策略

这个文件用于指导 Codex 如何处理工具安装、依赖管理、CLI、环境配置、项目内安装、全局安装和外部工具。

核心原则：

- 不要为了小任务乱装工具。
- 安装前必须先说明原因、影响和推荐方案。
- 项目依赖优先项目内安装。
- 跨项目通用 CLI 才考虑全局安装。
- 凭证、token、密钥、账号密码不写进聊天、记忆或项目文档。
- 遇到命令找不到，先判断环境、PATH、权限、包管理器状态，不要直接假设代码错了。

---

## 1. 什么时候读取本文件

遇到以下情况时，读取本文件：

- 需要安装新依赖
- 需要全局安装 CLI
- 需要判断项目内安装还是全局安装
- 遇到 `command not found`
- 遇到 PATH、权限、环境变量问题
- 任务涉及 Node / npm / pnpm
- 任务涉及 Python 包
- 任务涉及 Homebrew
- 任务涉及飞书 CLI
- 任务涉及 GitHub CLI
- 任务涉及 Playwright
- 任务涉及部署工具
- 任务涉及 Word / PPT / Excel / PDF / HTML 文件生成
- 任务涉及 API key、token、环境变量、`.env`
- 任务涉及外部系统连接

## 2. 安装确认规则

安装任何新工具或依赖前，必须先问 {{USER_NAME}}。

询问前先说明：

1. 为什么需要这个工具
2. 它是项目依赖、开发依赖、全局 CLI，还是系统工具
3. 建议安装在哪里
4. 会改哪些文件
5. 是否会影响其他项目
6. 有没有更轻的替代方案
7. 推荐方案是什么

没有确认前，不要执行安装命令。

---

## 3. 安装位置规则

### 项目内安装

适合 React、Vite、Playwright、ExcelJS、docx、pptxgenjs、项目专用 Python 包、项目测试工具、项目构建工具和项目专用 SDK。

如果这个工具是当前项目运行、构建、测试、生成文件所需要的，优先项目内安装。不要把项目依赖装成全局工具。

### 全局安装

适合跨项目都要用的 CLI，例如飞书 CLI、GitHub CLI、某些通用开发工具。

全局安装前必须确认。不要默认所有 CLI 都全局安装；如果只是某个项目用，优先项目内安装。

### 系统级安装

适合 Homebrew 安装的系统工具、数据库服务、图像 / 视频 / PDF 系统工具、需要系统权限的工具和会影响整台机器的配置。

系统级安装风险更高，必须先说明清楚。不要默认 `brew` 可用。

---

## 4. 环境观察规则

不要把某一次观察到的环境状态当成永久事实。

可以记录当前观察，但使用前必须重新验证。

当前环境的常见观察可能包括：

- Node.js 可用
- npm 可用
- pnpm 可能不可用或未加入 PATH
- Homebrew 可能不可用或未加入 PATH
- Python 3 可用
- VS Code App 可能已安装，但 `code` CLI 不一定可用
- Cursor App 可能已安装，但 `cursor` CLI 不一定可用
- Codex app 和 Codex CLI 已安装

正式 Codex 项目默认建议放在：

```text
{{CODEX_PROJECTS_ROOT}}/<项目名>
```

遇到 `command not found`、PATH 警告、permission denied、package manager not found、cannot find module、executable not found 时，优先检查环境而不是直接改代码。

如果需要更改 shell、PATH、CLI 配置，必须先问 {{USER_NAME}}。

---

## 5. Node / npm / pnpm 策略

默认使用 npm。不要默认使用 pnpm。

只有以下情况才建议安装或使用 pnpm：

- 项目模板明确要求 pnpm
- 项目已有 `pnpm-lock.yaml`
- 项目是 monorepo，pnpm 明显更合适
- {{USER_NAME}} 确认希望使用 pnpm
- 当前项目已有稳定 pnpm 工作流

如果项目已有 `package-lock.json`，默认继续用 npm。  
如果项目已有 `pnpm-lock.yaml`，再考虑 pnpm。  
不要在同一个项目里混用 npm、pnpm、yarn，除非明确知道原因。

---

## 6. Python 包策略

Python 包默认不全局乱装。

优先判断项目是否需要虚拟环境、`requirements.txt`、`pyproject.toml`、临时脚本，或系统 Python 是否足够。

安装 Python 包前必须说明是否项目内使用、是否需要虚拟环境、是否会污染系统 Python、是否有 Node 替代方案，以及为什么推荐 Python。

如果项目用了 Python 依赖，应建议记录到项目工具记忆文件。

---

## 7. Homebrew 策略

不要默认假设 Homebrew 可用。

如果任务需要 Homebrew，先说明为什么需要、是否有替代方案、是否系统级安装、安装后会影响什么、是否需要 {{USER_NAME}} 手动确认。

如果只是 Node 项目依赖，不要优先用 Homebrew。

---

## 8. 飞书 CLI 策略

飞书 CLI 适合创建飞书文档、发布 Markdown 到飞书、读取或整理飞书文档、发送飞书消息、操作飞书云盘、知识库、权限等。

但飞书属于外部系统。

默认规则：

- 安装飞书 CLI 前必须确认。
- 授权、扫码、OAuth 登录由 {{USER_NAME}} 手动完成。
- 发送消息、改权限、删除、移动、公开分享前必须确认。
- 默认先生成草稿或预览，不直接发送。
- 不把飞书 token、密钥、账号信息写入文件或记忆。

项目中使用飞书 CLI 时，应记录用途、只读/写入边界、常用非敏感命令和授权状态说明，但不记录凭证。

---

## 9. GitHub CLI 策略

GitHub CLI 适合查看 issue、PR、仓库状态、CI 输出和辅助代码协作。

必须先确认的动作：

- 创建 issue
- 评论 issue / PR
- 创建 PR
- merge PR
- close issue
- 发布 release
- 改仓库设置
- 删除 branch
- 修改权限

默认可以相对主动读取状态、issue、PR、CI 输出和总结仓库信息。

如果 GitHub CLI 需要登录或 token，由 {{USER_NAME}} 手动授权。不要把 GitHub token 写进聊天、记忆或项目文件。

---

## 10. Playwright 策略

Playwright 适合项目内安装，用于自己项目的 UI 自动化测试、本地页面验证、回归测试、截图测试、多浏览器检查和重复流程验证。

不适合绕过验证码、绕过风控、批量抓取受限网站、自动登录第三方网站或自动提交真实外部动作。

安装前必须说明为什么需要、是否项目内安装、会生成哪些文件、是否安装浏览器二进制、如何运行测试、是否写入 `package.json`、是否需要记录到项目工具文档。

---

## 11. Word / PPT / Excel 生成策略

生成 Word、PPT、Excel 文件时，先判断是一次性生成，还是项目长期能力。

一次性生成可以使用临时脚本或现有工具，但如果需要安装库，仍需先确认。

项目长期能力应项目内安装依赖，并记录到项目工具文档。

常见选择：

- Word：`docx` 或 Python 的 `python-docx`
- PPT：`pptxgenjs` 或 Python 的 `python-pptx`
- Excel：`exceljs` 或 Python 的 `openpyxl`
- HTML：通常不需要额外依赖
- PDF：根据项目需要选择工具，不要默认安装大型依赖

形成稳定报告生成流程后，未来可建议做成 Skill。

---

## 12. 部署工具策略

部署工具属于中高风险工具。

涉及部署前必须确认：

- 部署到哪里
- 是否公开访问
- 是否会产生费用
- 是否需要账号登录
- 是否需要环境变量
- 是否会暴露数据
- 是否会影响线上版本
- 是否需要回滚方案

如果项目进入部署阶段，应建议新增项目部署记忆文件。新增前必须先问 {{USER_NAME}}。

---

## 13. 环境变量和密钥策略

不要把以下内容写入聊天、记忆、日志、项目文档或代码注释：

- 密码
- token
- API key
- secret
- private key
- access token
- refresh token
- OAuth client secret
- cookie
- session
- 验证码
- 恢复码
- 支付信息

如果项目需要这些内容：

- 由 {{USER_NAME}} 本地配置
- 使用 `.env`
- `.env` 不应提交到 Git
- 可提供 `.env.example`
- `.env.example` 只能写变量名和占位符
- 不写真实值

---

## 14. PATH 和 command-not-found 排查

遇到 `command not found`，不要立刻安装。

先判断工具是否真的未安装、是否安装了但未加入 PATH、当前 shell 是否认识、Codex 环境和普通 Terminal 是否不同、是否权限限制、项目是否未运行 `npm install`、命令是否应该通过 `npx`、`npm run` 或本地路径调用。

需要修改 PATH、shell 配置、系统配置前，必须先问 {{USER_NAME}}。

---

## 15. 项目工具记忆

如果项目安装了依赖、CLI、工具或配置，应建议更新项目工具记忆文件。

默认建议位置：

`<project>/docs/codex/05_TOOLING.md`

如果项目已有特殊记忆结构，应按项目自己的工具记录文件执行。

记录内容包括工具名称、安装位置、安装原因、是否项目内安装、常用命令、是否需要授权、是否涉及外部系统、安全边界、替代方案、是否需要未来迁移或卸载。

不要记录敏感凭证。

## 16. 全局工具经验

如果某个工具规则跨项目长期有效，可以建议更新：

升级前必须先问 {{USER_NAME}}。

## 17. 工具研究规则

如果 {{USER_NAME}} 不知道该用什么工具，Codex 可以先做工具研究。

工具研究应输出可选工具、适用场景、安装复杂度、是否需要账号或授权、是否有安全风险、是否适合当前项目阶段和推荐方案。

不要直接因为某个工具流行就安装。工具推荐应优先考虑轻量、可维护、适合当前阶段、不过早复杂化、有退出方案、便于未来沉淀。

---

## 18. 复盘触发

安装新工具、配置 CLI、遇到 PATH 或包管理器问题、工具安装失败、授权流程中断、工具选择变化、项目引入长期依赖、部署流程出现、外部系统连接成功或失败、{{USER_NAME}} 对工具边界做新决定时，任务结束后应建议复盘。

写入前必须先问 {{USER_NAME}}。
