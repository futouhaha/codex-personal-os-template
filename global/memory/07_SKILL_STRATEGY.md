# Skill 策略

这个文件用于指导 Codex 如何判断、管理、创建、安装和维护 Skills，也用于指导 subagent 和长任务的使用策略。

核心原则：

- 不要为了显得高级而滥用 Skill。
- 不要一开始就把所有流程都做成 Skill。
- 只有重复、稳定、可复用的流程，才值得沉淀成 Skill。
- 创建、安装、修改 Skill 前，必须先向 {{USER_NAME}} 说明原因和影响，并等待确认。
- Skill 应该帮助 Codex 更稳定地执行重复任务，而不是增加理解负担。
- 如果一个流程还在探索中，先放在 prompt、项目记忆或全局记忆中，不急着做成 Skill。

---

## 1. 什么时候读取本文件

遇到以下情况时，读取本文件：

- 用户问“要不要做成 Skill”
- 同类任务重复出现
- 某个流程明显会跨项目复用
- 需要创建新 Skill
- 需要安装现成 Skill
- 需要整理或清理已有 Skills
- 需要判断某个流程放全局 Skill 还是项目 Skill
- 需要从 OpenClaw 迁移 skill / workflow 思路
- 任务涉及 subagent
- 任务较长，需要施工卡、状态锚点或中断恢复机制
- 任务做完后发现某个流程以后可能反复出现

---

## 2. 核心判断规则

判断一个流程是否值得做成 Skill，先看 5 个问题：

1. 这个流程是否会重复出现？
2. 这个流程是否有稳定步骤？
3. 这个流程是否有清楚的输入和输出？
4. 这个流程是否会跨项目复用？
5. 做成 Skill 后，是否真的能减少下次解释成本？

如果答案大多是否定，不要做成 Skill。

默认判断：

- 一次性任务 → 不做 Skill
- 还在探索中的流程 → 先写到 prompt 或记忆
- 重复 3 次以上的稳定流程 → 可以建议做 Skill
- 明显跨项目复用的流程 → 可以提前建议做 Skill
- 用户明确要求沉淀 → 可以提出 Skill 方案

---

## 3. 不要滥用 Skill

不要把这些内容做成 Skill：

- 一次性 prompt
- 还没验证过的流程
- 某个项目临时做法
- 只有一个项目会用的小规则
- 只是普通说明文档
- 还没有稳定输入输出的想法
- 需要频繁人工判断、还没形成流程的任务
- 本来写进 `AGENTS.md` 或记忆文件就足够的规则

不要为了“看起来系统化”而创建很多空 Skill。

如果一个流程还不成熟，先记录到 `09_REUSABLE_PROMPTS.md`、`08_CROSS_PROJECT_LEARNINGS.md`、项目经验文件或项目 prompt library。

---

## 4. 全局 Skill 和项目 Skill

### 全局 Skill

适合多个项目都会用、和 {{USER_NAME}} 长期工作方式有关、输入输出稳定、不依赖某个项目特殊目录或业务规则的流程。

默认位置应以 Codex 当前环境为准，常见可能是：

- `$CODEX_HOME/skills/`
- `~/.codex/skills/`

不要默认使用其他 agent 体系的 Skill 路径，例如 `$HOME/.agents/skills/`，除非 {{USER_NAME}} 明确说明该环境就是这样配置的。

适合全局 Skill 的方向：

- 任务复盘
- 项目记忆整理
- Project Onboarding
- 模糊想法转 Codex 任务
- 浏览器安全判断
- 工具安装判断
- 飞书发布
- 报告生成
- 长研究任务
- self-improvement
- Skill 创建和优化

### 项目 Skill

适合只服务一个项目、强依赖项目资料、目录、术语或业务规则、只在该项目内有意义的流程。

项目 Skill 的位置应遵守当前项目约定。常见可能是：

`<project>/.codex/skills/`

或项目已有的特殊技能目录。

---

## 5. Skill 建议规则

创建或安装 Skill 前，必须先提出建议，不要直接执行。

建议格式：

```text
## Skill 建议

### 1. 建议名称
...

### 2. 为什么需要这个 Skill
...

### 3. 触发场景
...

### 4. 输入
...

### 5. 输出
...

### 6. 建议放置位置
全局 / 项目

### 7. 是否已有替代方案
...

### 8. 是否会增加维护负担
...

### 9. 我的推荐
...

是否确认创建 / 安装？
```

等待 {{USER_NAME}} 确认后，才能创建、安装或修改 Skill。

---

## 6. 第一批 Skill 候选

这些不是必须立刻创建，而是候选清单。

- `project-memory-curator`：任务结束后判断哪些内容值得沉淀，并生成写入建议。
- `codex-task-planner`：把模糊想法整理成 Codex 可执行任务。
- `project-onboarding`：新长期项目开始前做问答，生成项目规则和记忆结构草案。
- `browser-safety-router`：判断浏览器任务应使用哪种工具并识别风险。
- `tooling-advisor`：判断工具安装位置、包管理器、PATH 和环境问题。
- `feishu-publisher`：生成飞书文档或消息草稿，管理发布边界。
- `report-builder`：生成 Word / PPT / Excel / HTML / Markdown 报告。
- `long-research-task`：多来源研究和结构化研究报告。
- `self-improvement`：记录失败、纠正、工具问题、能力缺口和过时知识。

---

## 7. 现成 Skill 研究规则

如果 {{USER_NAME}} 不确定某个能力是否已有成熟 Skill 可以复用，Codex 可以先做 Skill research。

Skill research 应输出可能可用的现成 Skill、来源和适用场景、是否适合 {{USER_NAME}} 的工作方式、是否安全、是否需要改造、是否更适合自己创建和推荐方案。

安装现成 Skill 前，必须先确认来源是否可信、是否会执行脚本、是否需要外部权限、是否会访问文件/浏览器/网络/账号、是否需要调整为中文规则、是否会和现有全局规则冲突、是否应该放全局还是项目。

---

## 8. Skill 内容风格

Skill 文件正文优先使用中文。

可以保留英文的内容：Skill name、文件名、目录名、命令、代码、参数、API 名称、包名。

Skill 内容应包含适用场景、不适用场景、输入、输出、执行步骤、安全边界、是否需要确认、写入记忆规则、与项目 `AGENTS.md` 的关系。

不要写太多无关背景。不要写成泛泛而谈的说明书。

---

## 9. Skill 维护规则

当 Skill 太多、描述不清、触发不稳定、和 `AGENTS.md` 或记忆文件冲突、内容过期、只服务某项目却放在全局、本来应该是项目文档、只是 prompt、多个 Skill 重复、使用后没有明显提升效率时，应建议清理或调整。

整理前必须先给方案，等待 {{USER_NAME}} 确认。

---

## 10. Skill 更新规则

修改 Skill 前，必须先说明为什么要改、改哪里、是新增/替换/删除/重构、是否影响已有项目、是否需要同步更新全局记忆或项目 `AGENTS.md`、是否存在安全风险。

不要偷偷修改 Skill。如果某次任务暴露了 Skill 的缺陷，应在任务复盘中提出修改建议。

---

## 11. Skill 和记忆的关系

Skill 不负责保存项目历史。项目历史应写入项目记忆。Skill 负责保存可复用流程。

判断方式：

```text
“这个项目现在做到哪里了？”
→ 项目记忆

“以后遇到同类任务应该怎么做？”
→ Skill 或全局记忆

“这是所有项目都必须遵守的红线吗？”
→ 全局 AGENTS.md

“这是 {{USER_NAME}} 的长期偏好吗？”
→ 全局记忆

“这是当前项目的特殊规则吗？”
→ 项目 AGENTS.md
```

不要把项目状态写进 Skill。不要把 Skill 当成记忆垃圾桶。

---

## 12. OpenClaw 迁移规则

从 OpenClaw 迁移思路时，重点迁移机制，不迁移工具细节。

优先考虑迁移记忆分层思想、长任务施工卡、状态锚点、外部动作确认、浏览器分级策略、self-improvement、long-research-task、video-insight-report、xiaoyuzhou-notes、browser-automation 安全边界、skill-creator / skill 优化流程、feishu 文档协作思路。

不建议原样迁移 OpenClaw 内部运行时细节、私有网络或远程浏览器命令、过多平台插件清单、过重 heartbeat、所有历史 daily 原文、与 Codex 不兼容的 ACP / runtime 细节或任何敏感配置。

---

## 13. Subagent 策略

不要默认使用 subagents。

只有当任务明显可并行、子任务边界清楚、子任务之间低耦合、每个 subagent 有明确输入输出、主 agent 能清楚汇总、额外成本值得、用户确认时，才建议使用 subagents。

适合 subagent 的情况包括大代码库探索、多模块 feature plan、多来源研究、PR 审查、前端/后端/文档/测试/安全分工、多方案并行比较、大型项目初步摸底。

不适合小 bug、小页面、简单文档、目标未说清、项目结构未建立或只是为了显得高级的任务。

---

## 14. 长任务策略

长任务不要黑箱执行。

以下情况属于长任务信号：

- 预计超过 10 分钟
- 涉及多个文件
- 涉及多个来源
- 涉及浏览器
- 涉及外部工具
- 涉及安装或配置
- 涉及登录态网页
- 涉及部署
- 涉及 subagent
- 涉及 background process
- 涉及多阶段交付
- 中断后需要恢复

长任务开始前，应先给施工卡，包含任务目标、当前理解、分阶段计划、会读取或修改哪些文件、可能使用哪些工具、风险点、状态锚点、中断后如何恢复、需要 {{USER_NAME}} 确认的事项。

等待 {{USER_NAME}} 确认后，再进入长任务执行。

---

## 15. 状态锚点规则

长任务应设置状态锚点，避免中断后丢失上下文。

可用状态锚点包括项目当前状态文件、项目任务日志、临时 `STATUS.md`、浏览器任务进度文件、任务阶段记录、Git diff、测试结果、终端日志摘要、文件修改清单。

状态锚点应简洁，不要变成聊天转录。如果任务中断，恢复时应先读取状态锚点，再继续。

---

## 16. Skill、prompt 和 memory 的区别

```text
一次性表达方式
→ 不保存，或临时 prompt

验证过、未来可能复用的 prompt
→ 09_REUSABLE_PROMPTS.md

当前项目专用 prompt
→ 项目 prompt library，若项目已创建

跨项目稳定流程
→ Skill candidate

项目历史和进展
→ 项目记忆

工具经验
→ 项目工具记忆或全局工具策略

强制红线
→ ~/.codex/AGENTS.md
```

不要把所有东西都技能化。

---

## 17. 复盘触发

同类流程第二次或第三次出现、{{USER_NAME}} 反复说明同一种偏好、任务中出现明显流程缺口、工具使用失败后找到稳定修复方法、浏览器或外部系统流程变复杂、长任务需要状态锚点、项目记忆整理重复发生、某个 prompt 多次好用、某个 OpenClaw 机制在 Codex 中复用成功时，应建议复盘是否需要 Skill 或流程沉淀。

写入或创建前必须先问 {{USER_NAME}}。

---

## 18. 更新规则

更新本文件前，必须先向 {{USER_NAME}} 提出建议，说明当前 Skill / subagent / 长任务策略哪里不够好、要改什么、为什么是跨项目规则、是否更适合写入某个项目、是否应升级为 `~/.codex/AGENTS.md` 红线，以及是否会让系统变重。
